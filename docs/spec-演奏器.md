# MidiPerformer — MIDI 演奏器

**状态**：ready-for-agent
**日期**：2026-09-18

---

## Problem Statement

我想在《三角洲行动》里用游戏内的口琴弹奏自己喜欢的曲子，但游戏里的乐器只能手动一个音一个音地按键，一首完整的曲子根本弹不下来。

现成的工具我试过两个，都不合用：

- **midikey-player** 是个纯播放器，能看谱能试听，但**不能编辑**——想改个调、删掉一段、把某条轨去掉，做不到。
- **harmonica-auto-player** 能把 MIDI 发成按键，但它是**一条龙黑盒**：导入就播放，中间没有任何可干预的地方。而且它的数据模型是**按秒存**的，想改 BPM 就得把所有音符的时间戳重算一遍。

我需要的是中间那一段：**下载一首 MIDI → 按我的需要改 → 再发成按键**。改的部分包括整曲速度、某条轨的音高、删掉不需要的声部、修几个别手的音。

另外，游戏里的口琴是**单声部**乐器——同时只能响一个音。网上下的 MIDI 大多是多轨多声部的，直接发出去会糊成一片。所以我还需要能看清每条轨是什么、能删掉多余的声部，并且程序能告诉我哪条轨是能弹的。

## Solution

一个 Windows 桌面程序，分成**编辑器**和**演奏器**两个窗口：

**编辑器**（主窗口）——导入 MIDI，所有轨堆叠显示成卷帘，直接在卷帘上改：拖动音符改音高和时值、方向键微调、空白处横拖删掉一段、每条轨单独改音色和移调、整曲改 BPM。改完存成工程文件，或者导出成 MIDI。

**演奏器**（独立置顶小窗）——挑一条**能弹的**轨，选好倒计时，点开始，程序切到游戏里把谱子发成按键。

关键的设计取舍：

- **音符只存 tick，不存秒。** 这样改 BPM 只动速度表里的一个数，所有音符一个字节都不用碰。
- **移调是轨的属性，永远不落进音符。** 想改回来随时改，无损。
- **演奏路径逐字复刻 harmonica-auto-player。** 那套时序是踩过坑调出来的（游戏按帧采样，间隔给不够就漏音），重写等于重新踩一遍。所以直接移植，并且用对拍测试证明移植没走样。
- **不读游戏进程。** 程序全程只做一件事：往系统里发按键。不枚举进程、不查前台窗口、不碰游戏内存。代价是没有「失焦自动急停」这条兜底，换来的是不会被反作弊盯上。

## User Stories

### 导入与曲库

1. 作为使用者，我想把一个 MIDI 文件拖进窗口就能导入，这样我不用先找目录再翻文件。
2. 作为使用者，我想导入时给这首歌起个名字，这样列表里显示的是一首曲子的名字而不是 `track03.mid`。
3. 作为使用者，我想让程序记住所有导入过的曲子，这样我下次打开不用重新导入。
4. 作为使用者，我想看到一个曲库列表，这样我能直接挑之前导入的曲子继续弄。
5. 作为使用者，我想从曲库里删掉一首不要的曲子，这样列表不会越堆越长。
6. 作为使用者，我想给已经导入的曲子改名，这样第一次名字起错了还能改。
7. 作为使用者，我想把改了一半的曲子存下来，这样我能分几次弄完。
8. 作为使用者，我想把改完的曲子导出成标准 MIDI 文件，这样我能在别的软件里用它。
9. 作为使用者，我想在曲库里一眼看出哪首改过、哪首没动过，这样我知道进度。

### 编辑 — 整曲

10. 作为使用者，我想改整曲的 BPM，这样我能把一首曲子调快或调慢。
11. 作为使用者，我想让 BPM 用一个**具体数字**显示和输入（比如 `76`），而不是一个百分比或倍率，这样我能对着原曲的标记直接填。
12. 作为使用者，我想在改完 BPM 后音符的位置和时值跟着一起缩放，这样曲子还是原来那首，只是快慢变了。
13. 作为使用者，我想撤销上一步操作，这样改错了不用重来。
14. 作为使用者，我想连续撤销很多步，这样我能一口气退回很远的地方。
15. 作为使用者，我想重做刚撤销的操作，这样撤多了能补回来。

### 编辑 — 音轨

16. 作为使用者，我想看到这首曲子里所有的轨，这样我知道它有几条声部。
17. 作为使用者，我想给每条轨选一个音色来**试听**，这样我能分辨哪条是钢琴、哪条是弦乐。（这只影响编辑器里的试听；发给游戏时永远是口琴那套键位。）
18. 作为使用者，我想给每条轨单独移调，单位是半音，这样我能把整条轨挪到口琴能弹的音区。
19. 作为使用者，我想给轨迹调一个 `+12` 或 `-12` 的整八度移调，这样我不用数十二下。
20. 作为使用者，我想删掉某条轨，这样多余的声部不会碍事。
21. 作为使用者，我想在删轨之前先确认一下，这样不会手滑删错。
22. 作为使用者，我想单独听某一条轨（独奏），这样我能判断这条是不是我要的旋律。
23. 作为使用者，我想把某条轨折叠起来只留一条标题栏，这样轨多的时候屏幕放得下。
24. 作为使用者，我想给轨改名，这样导出的 MIDI 里轨名是看得懂的。
25. 作为使用者，我想让每条轨的音域自动适配显示范围，这样音都在很窄或很宽的范围里时我都能看清。

### 编辑 — 段落与音符

26. 作为使用者，我想在卷帘的空白处横向拖一段就删掉那一段里所有的音，这样删前奏、删间奏不用一个一个点。

29. 作为使用者，我想用方向键微调选中的音符（左右移时间、上下移音高、加 Shift 改时值），这样在音符很密的地方我也能精确调整。
30. 作为使用者，我想框选一组音符一起移动，这样改一整句不用一个一个来。
31. 作为使用者，我想在改音符的时候能听见它，这样我知道改对没有。
32. 作为使用者，我想让改动吸附到网格上，这样我不用瞄得特别准。

## Implementation Decisions

### 分层

《架构整洁之道》的四层划分，**依赖方向一律朝内**：

```
App ──► Adapters ──► Core
 └────────────────────┘
Tests ──► 全部
```

落到目录上分成五块。（端口在理论上是 Core 内部的接缝，不是独立的一层；单列出来只是为了让边界看得见。）

| | 是什么 | 在哪 |
|---|---|---|
| **① 实体层** | `Song` `Track` `Note` `TempoMap` —— 数据长什么样 | `Core/Model/` |
| **② 用例层** | 编辑命令、单声部判定、工程进出、演奏事件表生成 | `Core/UseCases/` |
| **③ 端口层** | 接口。用例层引用的（出站）、适配层调用的（入站） | `Core/Ports/` |
| **④ 适配层** | 网关的实现 / Controller / Presenter | `Adapters/` |
| **⑤ 最外层** | Avalonia + Main | `App/` |

**① ② ③ 挤在同一个工程里。** 强制手段是**项目引用**：`Core.csproj` 不引用 Avalonia、不引用任何 Win32 相关的东西，编译器就不让写。这是全部测试方案成立的前提。

### 端口与网关是两样东西

| | 端口 | 网关 |
|---|---|---|
| 是什么 | 接口，一行实现都没有 | 类，真去调外部系统 |
| 在哪 | `Core/Ports/`（内层） | `Adapters/Gateways/`（最外层） |
| 说的是谁的语言 | 我们的（`Song` · `PhysicalEvent`） | 外部系统的（`SendInput` · 扫描码 · 文件路径） |
| 为什么在这 | 用例需要它才能编译 | 系统需要它才能被调用 |

**网关是默认的，端口是挣来的。** 每碰一个外部系统就有一个网关；只有当它需要第二个实现（假时钟 / 记录型 sink）时才补一个端口。所以 `SongLibrary`、`GlobalHotkeys` 是网关但没有端口——用例层根本不知道它们存在。

端口也不是「网关的接口」，是**用例需要的那一小块**：`IEventSink` 只声明 `Send` + `ReleaseAll`，`InputSender` 上其余的 `CheckElevation()` 之类由界面直接调，不经过端口。

### 四个工程

| 工程 | 内容 |
|---|---|
| `MidiPerformer.Core` | 实体 + 用例 + 端口，只引用 BCL + DryWetMidi |
| `MidiPerformer.Adapters` | 网关实现 / Controller / Presenter |
| `MidiPerformer.App` | Avalonia，含 Main |
| `MidiPerformer.Tests` | 单测 + 对拍 |

**DryWetMidi 住在 Core，不出现在 `Adapters` 里。** 它由 `UseCases/Project/SongProject` 独占——那个文件之外，程序里任何地方都不许出现 DryWetMidi 的类型。三条理由：

1. **S1 缝就开在 `SongProject` 上**，断言「导入 → 导出 → 再导入 = 同一个 `Song`」。解析放进网关，这条缝就跨不过去，S1 只剩 `.mproj` 半截。
2. **网关是明确不测的那一类。** MIDI 解析最容易错的地方正是 PPQ 换算和变速处理，放进网关等于把最该测的东西放进不测的筐里。
3. **要让 Core 用上网关就得再开一个端口**，而端口总数定死在四个。

DryWetMidi 是纯托管库，不碰 Win32、不碰 Avalonia，放进内层不破任何约束。**而且它是个纯工具库**——不存在「将来换个 MIDI 库」这回事，没有为它开端口、挡住它的价值。

移植进来的演奏逻辑**就放在用例层里**（`Core/UseCases/Perform/Repertoire/`），不单独成工程、不单独起名字。它没有独立的架构含义。

| `Preflight` | 游戏或系统加了新限制 |
| `Repertoire` | 键位 / 乐理规则变了 |
| `Dispatch` | 时序有问题、漏音 |
| `Safety` | 容错策略变了 |
| `StartPerformance` | 流程本身变了 |

`SongWalker` 从 `Perform/` 提到 `Timeline/`，因为试听也用它——留在 `Perform/` 里会让试听反过来依赖演奏。

### 数据模型

**音符只存 tick。** `Note` 是 `(Pitch, StartTick, LengthTicks, Velocity)`，没有秒这个字段。`TempoMap` 单独持有速度事件表，负责 tick ⇄ 秒的换算。

**改 BPM 的实现**：`SetBpm` 缩放 `TempoMap` 里的速度事件，音符数组**一个字节都不动**。界面上显示和输入的都是具体的 BPM 数字，不是百分比。

**移调是轨的属性。** `Track.Transpose` 是一个半音整数，播放和导出时才叠加到音高上，从不写回 `Note`。

**`Song` 不可变。** 每条编辑命令接收一个 `Song`，返回一个新的 `Song`。这个决定直接带来了撤销的实现方式（见下）。

### 撤销：装饰器

```
ISongEditor                        入站端口，每个编辑操作一个方法
SongEditor          : ISongEditor  真干活
UndoableSongEditor  : ISongEditor  装饰器，横切在所有命令外面
```

因为 `Song` 不可变、命令返回新 `Song`，**撤销栈就是一摞旧的 `Song` 引用**。装饰器只需在转发前后记账：命令产生了新对象就压栈并清空重做栈。

**撤销代码不切进任何一条命令内部**，`SongEditor` 里一行都没有。将来加一条新命令，撤销自动就有。

代价是内存（一万音符一份快照约 400KB），撤销栈**封顶 100 步**。

> 这也是 `ISongEditor` 值得开接口的唯一理由：装饰器给了它第二个实现。

### 演奏路径：边界处换单位

```
Song（tick）── RepertoireToSeconds ──► MappedNote[]（秒）── EventBuilder ──► 事件表
```

用 `TempoMap` 把选中轨的音符 tick → 秒，**只算这一次**，之后逐行走移植来的那套数学。编辑器那边保持 tick，演奏路径保持逐字复刻，两边都不将就。

### 演奏：逐字移植

从 `harmonica-auto-player@a14335c` 逐字搬进来的代码，除命名空间外不改一行，**就放在 `Core/UseCases/Perform/Repertoire/` 里**，和 `RepertoireToSeconds` 并排。搬进来之后它就是我们的代码了，跟着我们的项目走，和原版仓库再没有编译期关系。

`PlayKeys.cs` 不在移植范围内——原版里没有这个文件，键位表原本长在 `Engine/NoteMapper.cs` 里（`Keys` 和 `TopKey`），是我们把它抽出来单独成文件的。它**可以改**。

| 来源 | 搬进来的类型 |
|---|---|
| `Engine/InputTiming.cs` | `InputTiming`（三档时序预算，见下表）· `InputTimingProbe`（时序诊断） |
| `Engine/NoteMapper.cs` | `NoteMapper`（静态）· `MappedNote` · `MappingResult` · `Slot` |
| `Midi/MidiModels.cs` | `Music`（`Mod` / `NoteName` / `DegreeName`） |
| `Engine/PlaybackEngine.cs` | 只切出 `BuildSchedule` 方法本体 → 改名 `EventBuilder`；外加 `PhysicalEvent` · `ModState` · 四个 `K_*` 常量 |

**`PlaybackEngine` 本体不搬。** 它那套线程、暂停恢复、播放中实时移调是给「设备实时输入」和「播放中换谱」用的，我们不需要——派发由我们自己的 `Dispatcher` 负责。

「不许改」这条约束由 **01 的移植保真度对拍 + 02 的全链对拍**强制执行：谁改动了这几个文件，对拍立刻变红。约束靠测试强制，不靠命名约定，也不靠单独的文件夹。

**真要改的时候**（比如 12 里实机测出时序参数不对），那是**有意偏离逐字移植**，不是"改完重跑一遍对拍"就完事——01 的「与原版逐行一致」断言、对拍基线、以及 `Repertoire/` 的定位都要一起重新交代。这条路径是存在的，但它是**一次决定**，不是一次编辑。

**键位（写死在 `PlayKeys.cs`）**

| 音 | 键 |
|---|---|
| do re mi fa sol la si | `Z` `X` `C` `V` `B` `N` `M` |
| 高高音 do | `,` |

| 修饰键 | 含义 |
|---|---|
| 按住鼠标**左**键 | 降一个八度 |
| 按住鼠标**右**键 | 升一个八度 |
| 按住鼠标**中**键 | 升半音 |

三个修饰键全程只按住、不点击，`dx=dy=0`，光标不动、不会点到界面。

超出「基准八度 ±1 再加最高两个音」的音**跳过不发**，在卷帘上标灰。

**时序预算**（`InputTiming`，全部是物理毫秒，与播放速度无关）：

| 档位 | FrameMs | ModLeadMs | RetriggerMs | MinHoldMs | ReleaseGapMs | LeadMs |
|---|---|---|---|---|---|---|
| 稳健（30fps/卡顿） | 33.3 | 70 | 80 | 80 | 70 | 104 |
| 标准（60fps，默认） | 16.7 | 40 | 45 | 45 | 40 | 57 |
| 极限（高帧率） | 8.0 | 20 | 22 | 22 | 18 | 28 |

**事件表生成的核心不变量**（这是踩过坑的地方，重写必错）：

- 音符之间用**槽位**排开，不是靠「前音抬起 → 后音按下」的间隔。与前音重叠（含同刻起音）的音**顺延到前音之后，时值不变**。口琴单声部，同刻起音本来只能响一个；靠缩短前音去腾位置会产生零时长按键，游戏按帧采样时一帧都读不到，整段被吃掉。
- 修饰键比音键**早 `ModLeadMs`，且音键至少晚一帧**。
- 修饰键切换时**先松开所有不该按的，再按下所有该按的**（顺序固定）。
- 同键两次按下间隔 ≥ `RetriggerMs`；每次按下至少按住 `MinHoldMs`。
- 起点状态取自游戏**当前真实状态**（上一轮中断可能残留按键）。

### 播放循环

`UseCases/Timeline/SongWalker` 负责音乐时间 ↔ 物理时间的积分：事件表用**音乐时间（秒，与速度无关）**，工作线程按速度把物理流逝时间积分成音乐时间。`UseCases/Perform/Dispatch/Dispatcher` 按时间戳 sleep，最后 1.5ms 改成自旋等待。两者都在 Core 里，靠 `IClock` / `IEventSink` 注入，所以能用假时钟和假 sink 测。

**看门狗**（新增，原版里没有）：硬超时 = 曲长 + 5 秒，到点无条件停止并松开所有按键。超时时刻由事件表生成时顺带算出，运行时只剩一次比较。

### 单声部判定

**判据是「起音是否同时」，不是「时值是否重叠」。**

- 同一瞬间（**±30ms**）出现两个及以上的起音 → 判定为多声部
- 前音还在响、后音才起（连奏） → **不算多声部**，演奏时由槽位排开处理

这个区分很关键：用「时值重叠」做判据会把连奏的旋律误判成多声部，把用户真正想弹的那条轨藏起来。

能弹的轨按「最像主旋律」排序，第一条默认选中。

### Controller

**只有一个 `PianoRollController`**，因为它做真换算（像素 ⇄ 音高/tick、命中判定、拖动状态机）。

其余「点按钮 → 调命令」是纯管道，位置由 Avalonia 的 ViewModel 占着，不另造类。**方法体是原样转发的类不该存在。**

坐标换算（`PianoRollGeometry`）是纯函数，**Controller 方向（像素→tick）和 Presenter 方向（tick→像素）互逆**，放一起测一次往返恒等即可覆盖两边。卷帘编辑器最容易出的 bug 全在这里。

「开始演奏」那条链（预检 → 倒计时 → 启动 → 挂看门狗）是**用例** `StartPerformance`，不是 Controller。

### 端口

**出站（`Ports/Outbound/`）—— 只有三个接口**，每个都有具体理由：

- `IClock` + `IEventSink` — **演奏器跑起来没法调试**：它接管键盘、发到游戏里，只能盯着看。这种代码测试价值最高，所以 `Dispatcher` 放 Core，用假时钟和假 sink 测。
- `IAudioSink` — winmm 出声没法断言。但它和演奏器**共用同一个 `SongWalker`**（时间积分、变速、跳转），那是容易错的地方，测一次两边都覆盖。

其余地方不开接口。

**入站（`Ports/Inbound/`）—— 只有 `ISongEditor` 一个接口**，因为装饰器给了它第二个实现。`StartPerformance` 不加接口：Controller → 用例本来就是由外向内，不需要倒置，凭空加一个接口只是多一个文件、多一跳。**加接口只有两个正当理由：需要倒置，或者有第二个实现。**

### Request / Result

**只有一个 Request 值得做成具名类型：`StartPerformanceRequest`**——曲子、轨、基准八度、时序档位、倒计时，五六个参数，散着传是灾难。

编辑命令**不配 Request / Result**，直接收散参、返回 `Song`。曾经想给每条命令配一个 `XxxRequest` 和一个 `EditResult(Song, Changed)`，**砍掉了**：`Song` 不可变，「改没改」就等于「返回的引用是不是同一个」，装饰器用 `ReferenceEquals` 就能判断，`Changed` 字段是冗余的；其余每条命令的参数本来就只有一两个。

`PerformanceStartOutcome`（`Started` / `NotElevated` / `ImeActive` / `NoPlayableTrack`）是**枚举，不是 Result 对象**。它必须存在：预检的三种失败要给三种不同的中文提示，而文案是 Presenter 的事，Core 只回一个原因。

**这不是 DTO 层。** 它不映射任何外部格式，跟文件格式那件事无关——`.mproj` 那边依然是实体直接序列化。

### Main

`App.axaml.cs` 的 `OnFrameworkInitializationCompleted()` 是组装点，`Program.cs` 是入口。

**全程序唯一允许 `new` 具体实现的地方**（`new WinmmPreview()`、`new InputSender()`、`new SongLibrary(path)`），别处一律构造器注入。

`Tests` 是**第二个 Main**：装的是 `FakeClock` + `RecordingEventSink`。换配置就是换一个 Main，内层一行不改。

### 文件与存储

- 歌曲库存成 `.\songs\`（exe 旁边），文件名即曲名 —— 这是 `Adapters/Gateways/SongLibrary`，纯目录操作，**没有端口**
- 工程文件 `.mproj`，JSON，带 `Version` 字段管迁移。**不做 DTO 层**，实体直接序列化——只有一个消费者的文件格式，多一层映射是纯仪式
- **MIDI 的读写（导入与导出）都在 `Core/UseCases/Project/SongProject` 里**，用 DryWetMidi。这是唯一允许出现 DryWetMidi 的文件
- 导出 MIDI 是单独一个按钮，不覆盖 `.mproj`

### 安全边界

- **不枚举进程、不查前台窗口、不碰游戏内存。** 程序只往系统里发按键
- 界面常驻风险提示：虚拟输入违反游戏规则、可能导致封号、风险自负
- 无自动更新、无安装器、单文件自包含 exe
- 急停走 `WH_KEYBOARD_LL` 低层钩子，用 `LLKHF_INJECTED` 过滤掉自己发的按键，避免自触发

### 构建

C# / .NET 8 / Avalonia 11.3.20 / DryWetMidi 7.2.0 / `win-x64` 自包含单文件，`PublishTrimmed` 开。反射相关的程序集用 `TrimmerRootAssembly` 钉住（参考 midikey-player 的做法）。界面中文。

## Testing Decisions

### 什么算好测试

**只测外部行为，不测实现细节。** 具体到这一摊：断言的是「进去一串东西，出来一串东西」，不断言私有字段、不 mock 内部协作者、不检查方法被调了几次。

**缝开在最高的地方。** 一共四条，每条在自己那条轴上取最高点：

| | 缝 | 断言什么 |
|---|---|---|
| **S1** | `SongProject` ⇄ 文件 | 导入 → 导出 → 再导入 = 同一个 `Song`；`.mproj` 存 → 读回 = 同一个 `Song`。**tick 精确** |
| **S2** | `ISongEditor` 命令 | 每条命令后的可观察状态；撤销 N 次回到初始 |
| **S3** | `EventBuilder.Build` | 事件序列逐条相等（时间 / 键 / 按下还是松开） |
| **S4** | `PianoRollGeometry` | 像素 ⇄ (音高, tick) 往返恒等；命中判定 |

`S3` 是全局最高的缝：它在 `TempoMap` 之上（`Song` 自带 `TempoMap`，改 BPM 从这里流出去）、在 `SendInput` 之上、在 UI 之上。参考实现本来就是「先建事件表再派发」，这条缝是现成的。

**明确不测**：`Adapters` 里的 Gateway（SendInput、钩子、winmm、权限自检）、Avalonia 视图。缝开在它们上面，就是为了让这两层尽可能薄。

### 各模块测什么

**S1 — 工程往返**
- 真实 MIDI 语料导入后 tick 精确、轨数、每轨音色/移调/名称
- 导入 → 导出 → 再导入，两个 `Song` 逐字段相等
- 变速曲目：tick → 秒 → tick 往返恒等
- 坏文件、空文件、格式 0/1/2 各来一份不崩

**S2 — 编辑命令**
- 每条命令单独测：改 BPM 后**音符数组一字节不变**；移调后音符不变、只有 `Track.Transpose` 变；删轨后轨数 -1；删段落只删区间内的音；改时值/音高只动目标音
- 装饰器：N 条命令后连撤 N 次 = 初始状态；重做对称；撤销栈空时撤销无动作；新命令清空重做栈；栈封顶 100 步后最老的被丢掉

**S3 — 事件表**
- 边界用例：同刻起音、连奏重叠、跨八度、升半音、最高两个音、超范围跳过、空轨
- 断言五条不变量：修饰键先松后按且早于音键至少一帧；同键重触发 ≥ `RetriggerMs`；每次按下 ≥ `MinHoldMs`；零时长按键为 0；每个按下都有配对的松开
- 三档 `InputTiming` 各跑一遍
- **语料必须包含一首变速的曲子**，否则 `TempoMap` 中间变速那段测不到
- 看门狗超时时刻 = 最后一个音的结束时间 + 5 秒

**S4 — 坐标**
- 往返恒等：`像素 → (音高, tick) → 像素` 在任意视口和音域范围内成立
- 命中判定：命中音符头部 / 尾部 / 身体 / 空白
- 卷帘边缘、单音轨、极窄音域、极宽音域不越界

### 对拍

**这是「逐字复刻」这句话的证明。**

- 原版 `harmonica-auto-player` **一行都不改**。它已经导出了公开的 `BuildScheduleForTest`，直接用它，不需要 `InternalsVisibleTo`、不需要动可见性。
- 测试工程直接 `ProjectReference` 引用原版工程
- 同一批音符喂给两边，**逐条比事件的时间、键、按下还是松开**
- 语料：手写边界用例 + 真实 MIDI + 随机生成；三档 `InputTiming` 各跑一遍

跑的是原版代码本体，不是副本。

### 跑在哪

两套驱动，**缝还是同一条**（`Core` 的纯函数），只是回答不同问题：

- **NUnit 测试工程** —— 跑 S1–S4 全量，`dotnet test` 秒级反馈
- **exe 内置自检** —— 只跑几条 S3 冒烟用例，守**发布产物**。因为 exe 开 `PublishTrimmed`，裁剪会改变行为，只有真跑一次发布产物才算数

自检照搬 midikey-player 的做法：环境变量触发，`Program.cs` 第一件事就检查，写 PASS/FAIL 报告，外面用 `tools/run-selftest.ps1` 驱动、按退出码判定。

### 既有做法

- 两个参考 App 都没有测试；只有 DryWetMidi 库有 NUnit 测试工程（`Microsoft.NET.Test.Sdk` + NUnit4 + NUnit3TestAdapter）。
- **自检的既有做法在 `midikey-player`**：`GameSelfTest.cs` 跑纯逻辑用例，不建窗口、不注册热键、不碰按键与 MIDI 设备；`tools/run-selftest.ps1` 驱动，退出码 0/1/2/3。照这个来。
- `midikey-player/AGENTS.md` 记着一条真实回归（「选了一首之后别的点不动」），属于 S4 那一类。

## Out of Scope

- **循环播放** —— 明确去掉。放一首歌，放完停。
- **自由缩放** —— 明确去掉。固定 4 小节 + 导航条 + 方向键微调代替。
- **自动更新、安装器** —— 单文件 exe，双击就跑。
- **读取游戏进程、失焦自动急停、任何反作弊规避** —— 明确不做。
- **多乐器键位** —— 键位表写死一套口琴。每轨音色只影响试听，不影响演奏。
- **实时 MIDI 设备输入**（原版的 `LivePlayback`）—— 只做文件播放。
- **原版的 MACRO 导出、自动更新检查、最近打开历史** —— 不搬。
- **跨平台** —— Windows only。
- **多用户、云同步、分享** —— 自己用。

## Further Notes

### 参考仓库的归属

`harmonica-auto-player` 和 `midikey-player` 都是 `ChickenD233` 账号下的仓库，逐字移植没有授权问题。`harmonica-auto-player` 因为是收到腾讯投诉后停维护的，所以它的 README 顶部有一条暂停维护通知——**这不影响移植，但要清楚它的定位是「冻结的参考实现」而不是「会持续演进的依赖」**。

### 移植时最容易搞错的

`NoteMapper` 里 `Slot.Low`（低八度）对应**鼠标左键**、`Slot.High` 对应**右键**。三个源码位置一致（`NoteMapper.cs` 的 `Describe`、`MainWindow.axaml.cs` 的状态文案、`PlaybackEngine.cs` 的 `wantL/wantR` 赋值）。**搞反了每个跨八度的音都是错的**，而且听起来只是「有点怪」，不会明显报错。

### 单声部判定的陷阱

用「时值是否重叠」当判据会把**连奏的旋律**误判成多声部，把用户真正想弹的那条轨藏起来。必须用「起音是否同时」（±30ms）。原版 `MergeVoicesByPriority` 里的 `eps = 0.025` 是同一个阈值，这是它验证过的数；我们用 30ms 留一点余量。

### 为什么 undo 用装饰器而不是快照栈单独写

因为 `Song` 已经是不可变的、命令已经返回新对象，撤销栈天然就是「一摞旧引用」。把它写成装饰器，撤销就从一个「每条命令都要记得处理」的横切负担，变成一个「罩在外面、加命令自动生效」的横切能力。这是《架构整洁之道》里「用例不该知道交付机制」的一个具体兑现。

- 工程名和界面标题已定：工程 `MidiPerformer`，界面标题「MIDI 演奏器」，曲库目录 `.\songs\`。
- 目前没有配 issue tracker，本 spec 落在仓库内的 markdown 文件里，`ready-for-agent` 记在文件头的状态行。
