# 32: 曲库列表里的曲名不可编辑（改名只留顶栏那一处）

**What to build:** 左边曲库列表里的曲名**不再能编辑** —— 点它只当「选中这一行」，
不会冒出一个输入框。改名只剩**一处**入口：顶栏那格「歌曲名」框（回车提交）。

**几处要说清楚的决定：**

- **拆它的理由是误触。** 25 号把「改名」那颗按钮做成「名字本身可点」，
  代价是列表里**每一次点名字都可能是改名** —— 而列表里点名字最常干的事是「选中它看看」。
  这笔交易不划算，退回去。
- **鼠标和键盘一起拆**（2026-09-20 问过用户，选的是「连 F2 一起拆」）：选中一行按 F2
  也不再进编辑。**只拆一半是不行的** —— 那样「曲名不可编辑」这句话就有了例外，
  而下一个人看不见这个例外（他会以为这个列表压根不能改名）。
  代价明码写在这儿：**没打开的那首歌，键盘改不了名**，得先打开它、再用顶栏那格改。
- **顶栏那格是唯一的改名入口**：`MainWindow.OnSongNameKeyDown` → `RenameTo`，
  改的是**当前开着的那首**。它本来就有这一条路（25 号之前，曲库那条改名走的是弹框
  `Dialogs.AskNameAsync`，顶栏走的是这一格），现在曲库那条整条撤掉，这一格留下来。
- **`RenameRequested` 事件和 `RenameRequest` 记录一起删。** 面板不再喊改名之后，
  窗口那个 `OnRenameRequested` 处理器就是死代码。留着比删掉坏 ——
  留着的话，「曲库列表能改名」这句话在代码里还有一个入口的样子，下一个人会照它去改。
- **曲名那一格留着 ToolTip**（看被省略号吃掉的完整曲名），但光标从 `IBeam` 改回箭头：
  `IBeam` 是在承诺「这儿可以打字」，现在打了没用了。
- 行的结构从「名字文字 + 名字框」两半变回**一个 `TextBlock`**，`Row` 记录跟着消失，
  `_rows` 直接存 `ListBoxItem`（它本来只需要 Item 那一半）。
- **双击名字现在会打开这首**（从前第一下就进了改名、第二下落在框里，所以被拦着）。
  这是拆掉改名之后自然变好的地方，不是副作用。

## 哪些是测出来的、哪些只是写出来了

**测出来的**：上面每一条勾都挂着 `.scratch/verify-32.ps1` 的一次真实运行（**34 条 OK、0 条红**，
`全过`，收工还原「cargo.mproj / Carulli_Duetto_No2_Op4.mproj（逐字节和开工前一致）」）。
它是真机跑的：起 `MidiPerformer.exe`、UIA 找元素、合成鼠标真点、真悬浮、真双击、
真往盘上改文件名再改回来。**每一个数都是量出来的**（0 个框 / 22 个字符 / 11 条轨 / 2 个文件 /
那个哈希），不是「应该是」。

**只是写出来了**（没测，或者测不到）：

- **F2 那一条是半强度的判据。** 它只证明「F2 之后行里没有输入框」——
  而「F2 根本没送到列表」也**同样**满足它。要真钉死「F2 到了、只是没人接，
  那条键盘路是拆掉的而不是坏的」，得在 `ListBox` 上挂一个计数器。没做。
- **光标形状没人看过**（那一项没勾，理由写在那儿了）。
- **「双击打开」只量到结果**：曲名框变成 `cargo`、轨数 11。
  「双击会不会顺手把行选中、第一下有没有多余动作、手感对不对」归人眼。
- **改完名之后，`.mproj` 头里的 `Name` 字段和文件名可能对不上。**
  改名只动文件名 —— 这正是 §7 那条哈希断言（内容一个字节没动）的另一面：
  文件里的 `Name` 还是改名前那个。界面读的是**文件名**，所以此刻看不出问题；
  但下一个人要是去读 `Name`，会读到旧名字。**这是知道的代价，不是漏掉的 bug。**
- **鼠标点进顶栏那一格再回车，行不行，没人试过**（见「坑」第 1 条）——
  而那一格现在是唯一的改名入口，这一条只能真人验。

## 给下一个人的坑

1. **合成鼠标点进顶栏「歌曲名」框，回车到不了 `OnSongNameKeyDown`。**
   量到的事实（`probe32c/d/f` + `verify-32` §7 三种写法都复现）：鼠标点进去之后
   框里**字进得去**、`HasKeyboardFocus=True`，但回车没人接 —— 连 `Ctrl+A` 都不生效，
   新字是插在原串中间（读到 `Carulli_DuettZZQQo_No2_Op4`）。
   同一格换 UIA `SetFocus()` + `ValuePattern.SetValue` + 回车**就通**（21 号 `JumpBox` 那套）。
   **根因没查出来**：`WindowFromPoint` 在那个点上是主窗、不是浮层（`probe32e`），
   所以不是「点在别人身上」这种解释。
   → **验证脚本一律走 UIA 那条路**（`verify-32` 的 `顶栏改名为`），不要用合成鼠标点它。
   → **那一格现在是唯一的改名入口**，所以「人手点一下、按回车，到底行不行」得**真人试一次**
   （10 秒的事）。这是这一票唯一不能靠脚本收口的判据。
2. **没有闸门的脚本点鼠标 = 往别人的窗口里打字。** 这一票的探针（`probe32b/c/d`）就是没闸门，
   正赶上 VS Code 整个盖在 app 上面（`probe32e` 量到：
   `Chrome_RenderWidgetHostHWND` 铺满 0,0 3072x1824，标题是那个 `.txt`），
   于是那几下鼠标点进了 VS Code，跟着的 `SendKeys('^a') + 名字 + 回车` 也进了别人的编辑器。
   **规矩**：任何合成鼠标 / 键盘之前，先 `GetForegroundWindow() == 主窗` **且**
   `WindowFromPoint(落点)` 就是主窗，两条都真才发；缺一条当场 throw。
   `verify-32` 的 `要前台` / `点` / `打字` 和 `verify-25` 的 `改名走顶栏` 都是照这个写的 ——
   **新写探针的第一件事是抄这几行**，不是先跑起来再说。
3. **`probe4.mproj` 那颗雷。** 上一轮的改名实验把 Carulli 那份数据留在了 `probe4.mproj` 这个名字上，
   于是 `probe32b` 找不到那一行、曲子没载进来、曲名框还是灰的，量出来一整片「什么都没发生」——
   **四个格子全是废数据**。已经改回 `Carulli_Duetto_No2_Op4.mproj`（340831 字节，
   和 `publish\songs` 那份逐字节一致）。
   **探针的教训**：找不到那一行要**当场停下并喊出来**（`probe32c` 起改成 `throw`），
   不能接着把「什么都没发生」记成数据 —— 那种数据比没有数据更坏，它会进工单。
4. **Avalonia 的 ToolTip 是另一个顶层窗**，不挂在主窗上：量到 `0x4607AE`、
   类名 `Avalonia-<guid>`、**612x94 @932,448**，出现在悬浮那一格下方。
   所以「悬浮看全名」只能靠 UIA 的 `HelpText` 量（`Current.HelpText`），
   别指望 `WindowFromPoint` 在那一刻拿到主窗。
   （26 号那个坑的另一半：窗口被压在任务栏底下时，底下那几行的 ToolTip 永远弹不出来。）
5. **删的是曲库那条，轨头那条还在。** 搜 `RenameRequest` 会同时看到
   `TrackLaneView.RenameRequested` / `MainWindow.OnTrackRenameRequested` ——
   那是 25 号另一半（轨头名字就地可编辑），**别顺手删**。
   这一票删掉的只有：`SongLibraryPanel` 的 `RenameRequested` 事件、`RenameRequest` 记录、
   `MainWindow.OnRenameRequested` 处理器，以及面板里那套「名字文字 ↔ 名字框」的两半结构
   （`Row` 记录跟着没了，`_rows` 现在直接存 `ListBoxItem`）。
6. **顶栏那一格的改名语义没变**：改的是**当前开着的那首**，改的就是曲库里的文件名。
   所以「给一首没打开的歌改名」现在没有入口 —— 得先打开它。这是「鼠标 + F2 一起拆」明码写在
   上面的代价，不是漏掉的路。
